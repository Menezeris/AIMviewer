### D-195 - IFC 4.3 schema in the repo, entity manifest `entity_types`, `properties._attributes`

**Date:** 2026-11-05 · **Status:** approved (Samuel 5 Nov, plan round of platform step 4, "plan yes, 1 to 7 as recommended", relayed by the orchestrator under D-193, #60) · **Builds on:** D-046 (IFC-first), D-048 (binary relationships), D-051 (`relationship_types` manifest), D-022 (properties convention), D-183 (revision copy, `_class` in `ifc_rev_objects`), D-189 (projects) · **Plan:** platform plan 3.4, round 8 (3.5), chapter 6, 7.3 points 1 to 4, 7.5 R1, R5, R9, R10

**Context:** no repo held the IFC schema. The ETL has ifcopenshell (machine schema: entities, attributes, enums, no definitions or psets), so a session checking IFC-first (D-046) had to search the web. The platform plan needs new IFC entities (tasks, approvals, events) without a migration per class (round 8), node types decided by `ifc_type` and the IFC class tree (R5, R9), and relationship validation against the schema (R10, next step). That needs the whole class tree as data. AGENTS.md said "IFC attributes are columns", which conflicts with "a new entity is a row, not a migration".

**Decision:**
1. **Schema access.** Git submodule `vendor/ifc4.3` of `buildingSMART/IFC4.3.x-development`, pinned to `424cadb` (HEAD on 5 Nov, already cited in the plan, R4). Sessions fetch it shallow, blob-filtered and sparse (`docs/schemas`, `reference_schemas/psd`, about 21 MB) with `scripts/ifc-schema/fetch.sh`. CI and the app build do not need it. CC BY-ND 4.0: used and cited, never modified (`vendor/IFC4.3-NOTICE.md`). AGENTS.md rule: look up every new attribute, entity, enum or relationship there first.
2. **Entity manifest `entity_types`.** One global table (no `project_id`) with every entity of IFC 4.3 (876), generated by `etl/entity_manifest.py` from ifcopenshell `IFC4X3_ADD2`, whose entity set equals the entity files at `424cadb`. Columns: `ifc_class`, `supertype`, `ancestors` (root first), `is_abstract`, `is_root` (IfcRoot subtype), `is_node` (stored as a node in `objects`: every IfcObjectDefinition subtype plus the resource entities with identity of R1: IfcDocumentInformation, IfcDocumentReference, IfcApproval, IfcObjective, IfcMetric, IfcPerson, IfcOrganization), schema layer and package, own explicit attributes with enum values inline, schema version, source commit. No definition text from the schema docs (CC BY-ND); tools read the files by path. `entity_is_a(child, ancestor)` answers R9 categories and R10 checks from `ancestors`.
3. **Generated and checked.** The migration with the rows is checked in. `python -m etl.entity_manifest --check` regenerates it and fails on drift; a pytest does the same and a CI step installs ifcopenshell to run it.
4. **`properties._attributes`** (declared extension, SCHEMA §4): IFC attributes of a node that have no column, by IFC attribute name. Value entities without identity are nested objects with a `_class` key, as in `ifc_rev_objects` (IfcTaskTime, IfcTaskTimeRecurring with IfcRecurrencePattern, IfcEventTime, IfcCostValue, IfcPostalAddress, IfcTelecomAddress). IfcActorRole stays on the edge. A column is added only for values that are searched (round 8). This replaces "IFC attributes are columns" in AGENTS.md. A read-only report function lists `_attributes` keys the manifest does not know; nothing is rejected.

**Rejected:** a full submodule checkout (118 MB per session); fetching the schema in CI or the Vercel build; only the IfcObjectDefinition subtypes (R10 needs relationship and resource classes too); a recursive function instead of `ancestors[]` (the R10 trigger then needs recursion per row); copying definitions into the table (license, and the files are already there); a validation trigger on `_attributes` (would reject existing data).

**Consequences:** new IFC node types need no migration (`entity_types` already has them); the R10 validation step reads `entity_types`. Moving the pin is a new decision. Psets from the schema go into the `ifc_property_definitions` pattern later, not in this step.
