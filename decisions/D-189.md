### D-189 - AIMviewer becomes multi-project: project_id on project-bound tables, models identified by UUID, per-project codes, one project resolver

**Date:** 2026-11-04 · **Status:** approved (Samuel 4 Nov, round 1 answers below; number reserved in #60). Migration applied to production 5 Nov on Samuel's yes, after a fresh backup. · **Builds on:** D-188 (platform schema), D-026 (service_role), D-010 (identity), D-088 (IfcProject node), D-183 (revision container is the truth), D-059/D-060 (RPC rules), D-079 (live channel); document "Assetin platforma - stav, rozhodnutia a plán" (3.5, round 8, 7.3 point 8)

**Context:** step 3 of the platform plan. AIM holds one building (OCB) and every key assumes it: model codes `ASR`/`VZT` are global keys (revisions, containers, the ifc_rev_* revision copy, archive paths), clash and IDS codes, BCF numbers and saved view names are global, and the code reads "the" IfcProject. Round 8 decided: `project_id` on every project-bound table, all existing data to OCB (hosted by Assetin), filtering through one helper and a parameter in RPCs and `v_*` views, people and organizations global (A1), RLS after the demo.

**IFC basis:** IFC 4.3 IfcProject "establishes the context for information to be exchanged or shared, and it may represent a construction project but does not have to"; at most one per exchange (IfcSingleProjectInstance); `Name` is mandatory (HasName). IfcRelDeclares: "Every object (as subtype of IfcObject) has to be declared within the context of a single IfcProject ... This declaration is transitive." So `project_id` on a node materializes the IFC context; it is not an AIM invention. IfcContext is abstract and its other subtype, IfcProjectLibrary, is for referenced libraries, so IfcProject is the only fitting class. IFC defines IfcProject per exchange: every file of a project carries its own instance with its own GlobalId (OCB: ASR `2Xj8NwiwHD_hFSIx764rKm`, VZT `1ujCBri_f5JOmrrxrlahvh`, both `Name = OCB`). Therefore the AIM node is the canonical project and each file's IfcProject maps onto it by `Name` = project code; the other GlobalIds are aliases of the node (`ifc_guid_aliases`). IfcPerson and IfcOrganization are resources and are not declared, which matches A1; participation of an actor can later be a declaration edge from the project, without a `project_id` on the person.

**Decision:**
1. **Project identity.** A project is the `objects` node with `object_type = 'project'`; its `id` is the platform project id (`platform.projects.id`, step 7 adds that row) and its `object_ref` is the project code (`IfcProject.Name`). OCB = `9e2dfcba-437b-43d3-a925-0dd29f195b38`. The project node has `project_id = id`.
2. **`project_id uuid` references `objects(id)`** on: `objects` (NULL only for person and organization), `relationships` (NULL only for `rel_member_of`), `information_containers`, `model_revisions`, `model_tasks`, `saved_views`, `clash_tests`, `clash_runs`, `ids_documents`, `ids_runs`, `derivation_runs`, `verification_runs`, `icdd_imports`, `drawing_link_overrides`, `ifc_guid_aliases`, and nullable on `mcp_call_log`. Tables reached through a parent FK (1:1 suffixes, pages, results, versions, reviews, container revisions, guid history) take the project of the parent and expose it in views. Global: persons, ifc_actor, ifc_application, classification, relationship_types, ifc_property_definitions, derivation_rules, the `library` schema. No FK to `platform.projects`: AIM does not read `platform` and the OCB row there comes in step 7.
3. **Existing data goes to OCB.** Columns are added with a constant DEFAULT (metadata only). The DEFAULT, the old global unique keys and the OCB wrappers of the old function signatures stay until the app and ETL write `project_id` themselves; then a cleanup migration drops them. The HVAC model's IfcProject becomes a GUID alias of the OCB node, so its three documents now attach to the OCB project.
4. **Models are identified by UUID** (Samuel: "every project can have many different models with various names and codes, not every project will have ASR - UUID is important"). The model is its container: `information_containers.id`. The code (`ASR`) is a label unique within a project. `model_revisions` gets `container_id`; the revision copy (`ifc_rev_*`) is keyed by `model_revision_id` (so it needs no own `project_id`). Revision stamps (`{model: revision}` in run rows) stay keyed by the code, which is unambiguous inside the row's project; the stamp functions take the project (`project_model_revisions_at`, `project_revisions_stale`). No code may assume a model code exists.
5. **Per-project uniqueness** (Samuel: per project): clash test code, IDS code, BCF topic number, saved view name and the 'last' view, container identification, active GUID alias. `object_ref` stays unique across the platform (3.5); an IFC GUID is unique only within a project.
6. **Filtering:** views carry `project_id`; RPCs used by the app and LLM take `p_project uuid` (old signatures stay as OCB wrappers until the app is deployed); the relationship validation trigger rejects edges across projects (global actors and classification excepted).
7. **Current project in the app:** one resolver (`lib/project/`), default from configuration (`AIM_DEFAULT_PROJECT`, default `OCB`), override with `?project=<code>` on pages and on the MCP connector URL (`/api/mcp/<token>?project=OCB`, Samuel: connector URL, no change to the 31 tool schemas). The request project rides in the existing caller AsyncLocalStorage; cached reads take it as an explicit argument. Step 6 replaces only the source of the code (session instead of URL or configuration).
8. **ETL:** `--project <code>`; every file must have `IfcProject.Name` equal to the code; IfcProject is read from every file, not only the main model; every insert writes `project_id`.
9. **Delivery** (Samuel: one D-record, three PRs): PR 1 migration with SQL test and SCHEMA.md, PR 2 app, PR 3 ETL; a small viewer fork change (cache prune keyed with the project) only when a second project is loaded in one browser.
10. **Migration history:** `20261102190000_ids_guard_search_path` is live in the database (both guard functions have `search_path=public`) but missing from `supabase_migrations.schema_migrations`; its row is recorded without DDL.

**Rejected:** platform-unique model codes (`XYZ-ASR`): codes would carry the project, and Samuel wants UUID identity; a per-tool `project` parameter on all 31 MCP tools: longer descriptions and evals for a need that step 6 removes; FK from AIM tables to `platform.projects`: crosses the D-188 boundary and the row does not exist yet; `project_id` on every child table: duplicates what the parent FK already says and can drift.

**Risks:** the revision copy rewrite (~400k rows) is the only real data update, so it is measured on a restored backup first; old signatures must stay until PR 2 is deployed (release train D-116); the ISR cache key must contain the project or one project's page could serve another's data.

**Open:** R12 (write log with the person): RPCs or `request.headers`, touches step 3 only at the edges; `derivation_rules.enabled` is global today but probably a per-project setting; when to drop the DEFAULT; RLS policies after the demo; a project-scoped coding scheme for `object_ref` when a second project collides (D-033).

**Addendum PR 2 (app, 5 Nov, Samuel's round in the PR 2 session):**
- **Page project = session cookie** (Samuel chose it over sessionStorage alone): `proxy.ts` turns `?project=<code>` on a page into the browser-session cookie `aim_project` plus a request header for the same render, because the layout cannot read `searchParams`, client links do not carry the parameter and the viewer calls `/api/*` itself. `?project=` (empty) or `default` clears it. `components/live-channel.tsx` mirrors the code into sessionStorage, and a live command of another project navigates instead of applying in place. API routes resolve `?project=`, then the cookie, then the default (`lib/project/request.ts`, `withRequestProject`); the MCP connector only its URL. The viewer layout is no longer ISR-cached; its data stays cached per project.
- **Cached reads** take `projectId` as their first argument (`cachedProjectRead` in `lib/data/revalidate.ts`, key and tag `aim:<projectId>`); writes clear their project through `revalidateProject`; the ETL tag `aim` still clears everything.
- **Models come from the DB** per project (containers with a current revision, URL from the revision's archive `location`); the hardcoded ASR/VZT list is gone. **The label is the model code** until a separate decision on a naming convention and the discipline from the STEP header and the IFC classes (Samuel: nothing hardcoded, decide later). The IFC engine keys its cache by container id; in-memory clash runs and default clash tests are per project (a project without ASR and VZT lists no default tests). The `model` enum of the engine tools lists the request project's codes.
- **BCF API:** the BCF `project_id` is the project code and rides in the path (`/api/bcf/2.1/projects/OCB/...`), because the viewer calls the API cross-origin without cookies; the legacy `aim` stays accepted. BCF numbers are still drawn from one global identity, so they are unique per project but a second project does not start at 1; per-project numbering needs a trigger in the cleanup migration.
- **Guard:** `lib/project/project-scope.test.ts` fails when a project-bound table or view is queried without `project_id` (exceptions listed with a reason). Persons and organizations are global: generic object reads use `project_id = p or project_id is null`.
- **D-190 (from the PR 3 session):** a new project archives its models by container UUID (`ifc/archive/<container id>/vNNN.ifc.gz`); the app takes the URL from `model_revisions.archive_path` and the code from the DB, never from the path. Outside OCB `object_ref` is `<code>:<ref>` with the plain ref in `properties._ref`; showing and finding by `_ref` in a non-OCB project is a follow-up (OCB is unchanged).

**Addendum incident 5 Nov (PR 2 reverted, #419):** after the #417 deploy every `rel_contained_in_spatial_structure` request with `project_id=eq.<OCB>` timed out (57014). Cause: `objects` had no planner statistics for the new `project_id` (added through a constant DEFAULT, 58 rows updated, below the autovacuum threshold; last analyze 29 Oct) and `ifc_guid_aliases` none at all, so the planner expected about 0.5 % of the rows for OCB and chose nested loops over the view's CTEs. On a restore of production with the same statistics state the app's query took 37.4 s; after `ANALYZE` 0.06 to 0.12 s. Fix: migration `20261105113933_analyze_project_columns.sql` (statistics only, no data or schema change), applied before PR 2 is re-applied (Samuel, relayed 5 Nov, #60). A migration that adds a column that queries filter on runs `ANALYZE` on its table.

**Addendum cleanup migration (5 Nov, Samuel's plan round in the cleanup step session, "Yes" to all five points):**
- **Migration `20261105120000_multi_project_cleanup.sql`** (decision 3 above), one transaction. It removes the DEFAULT OCB on every `project_id` column and on `p_project`, the old global unique keys, the OCB wrappers of the old function signatures and the three `(model, revision)` indexes of the revision copy. A writer that does not name the project gets an error.
- **`p_project` keeps `DEFAULT NULL`** in the six RPCs, because Postgres needs a default after a defaulted parameter and the parameters before it have defaults. NULL raises "p_project is required" (`project_required`), so a missing project is still an error.
- **Fill triggers** (Samuel: drop): the four `trg_ifc_rev_*_model_revision` triggers are gone (the ETL writes `model_revision_id`). `trg_model_revisions_container` stays as a check only: `container_id` is required and must be the model's container in the row's project.
- **BCF numbers per project** (Samuel: counter table): `bcf_topic_counters (project_id, last_number)`, taken by the insert trigger of `model_tasks` under the row lock of `on conflict do update`. A new project's first topic is 1. OCB keeps its numbers and continues after the last value of the former global identity, so no number it handed out comes back.
- **Callers found by the inventory** that still relied on the transitional pieces, both fixed before the apply: the library release (`library.publikuj_ids`, called by `library_vydaj`) inserted IDS without a project and looked them up by code alone; it now takes `p_project` (the request project of the editor route), so a release goes into one project's catalog. The project versions come in a separate additive migration `20261105115915_library_release_project.sql`, applied before the cleanup PR is merged, so the old app (8 arguments) and the new app (with `p_project`) both work during the deploy (`LIBRARY_RELEASE_ENABLED` is on); the cleanup migration only drops the old signatures. The OCB workflows `uloha` and `revision-copy` call `ifc_rev_storey_elements` without the project; they now pass the OCB id (OCB #25, merged 5 Nov).
- **Older SQL tests** include `supabase/tests/_legacy_ocb.sql`, which puts back the OCB default and the id fills inside their own rolled-back transaction; `multi_project.sql` does not, and checks the target state.
- **Order** (Samuel: after the callers are live): #420 (statistics), #421 (re-apply of #417) and OCB #25 are merged and live; then the additive library migration, then this PR, then the apply after Samuel's yes, a fresh backup and a restore test. The migration ends with `ANALYZE` of the tables it changes (rule of the incident addendum).
