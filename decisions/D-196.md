### D-196 - Relationship validation per the IFC schema (R10) and the transaction log (R2, R12)

**Date:** 2026-11-05 · **Status:** approved (Samuel 5 Nov in the step session: "A to I as recommended, C per PLATFORM.md §5.3"; number from the orchestrator, #60) · **Builds on:** D-046 (IFC-first), D-048 (binary relationships), D-051 (`relationship_types` manifest), D-188 (platform boundary), D-189 (projects), D-195 (`entity_types`, `entity_is_a`) · **Plan:** platform plan 7.3 points 4 to 8, 7.5 R2, R10, R11, R12, R14, chapter 6, chapter 7 C11; AIMforked PLATFORM.md §3, §5.2, §5.3

**Context:** `relationships_validate` checks the ends only against lists of AIM `object_type` values. R10 asks for the IFC rule: the `ifc_type` of each end is a subtype of the declared type of the Relating and Related attribute of the IfcRel class. R2 and R12 ask for one append-only log of every write to the graph and to platform, with the person from the session setting `app.person_id`, and IfcOwnerHistory derived from it (7.3 point 5). On 5 Nov in production all 4,749 active edges already pass the IFC rule; the only failures are 374 ended `rel_associates_document` edges whose 65 document nodes have no `ifc_type`. The ETL rewrites unchanged rows on every load (`relationships` 128,848 updates for 13,150 rows, `objects` 22,419 for 2,899).

**Decision:**
1. **End types in the manifest.** `relationship_types.from_ifc_types` / `to_ifc_types`: the declared IFC type of each end (a SELECT expanded to its entities), read from ifcopenshell `IFC4X3_ADD2` by `etl/manifest.py` (`--sql-ifc-types`) and checked for drift against the migration. aim_* types state their own; an empty list means no IFC check at that end (object_type rule only). A classification end (`classification_references`) counts as IfcClassificationReference. `ifc_check` per rel_type: `off`, `warn`, `enforce`.
2. **Rollout (A).** PR 1: columns, generator and the report view `v_relationship_ifc_violations`, all rel_types `off`, write behaviour unchanged. PR 3: `relationships_validate` checks the ends with `relationship_ifc_end_ok` (subtype through `entity_is_a`); `warn` raises a WARNING and the view lists it, `enforce` rejects. A rel_type moves to `enforce` once the view shows 0 active violations for it. Ended edges are not rechecked. The narrower object_type rules stay on top until R5/R9 remove them.
3. **Document nodes (B).** A node with `object_type = 'document'` is IfcDocumentInformation; the PR 1 migration fills the 65 missing values and `etl/doc_upload.py` sets it from then on.
4. **Actors (C, PLATFORM.md §5.3).** The From end of `rel_assigns_to_actor` is IfcActor only, as in the schema. A person or organisation acting in a role is an IfcActor node (`object_type = 'actor'`) whose TheActor points to the IfcPerson or IfcOrganization (in `properties._attributes`, D-195). `actor` is added to the allowed object types; person and organization stay until the narrower rule goes. The ETL path that writes person/organization -> object (`etl/transform.py`, 0 rows in production) must create the IfcActor node before this rel_type is enforced.
5. **aim_* without an IFC class (D).** capture and capture_media have no IFC class; `aim_rel_capture_located` To end = IfcSpatialElement, the other ends are not checked.
6. **Who writes (E).** A PostgREST `db-pre-request` function copies the request headers `x-aim-person-id` and `x-aim-source` into `app.person_id` and `app.source`, trusted only when the JWT role is `service_role` (only the AIM server holds that key; `anon` has no rights). The app's server client sends both on every request; writes of the fork to `public` go through the AIM API (PLATFORM.md §3) and carry the same header. The ETL and the fork's own writes to `platform` use `SET LOCAL app.person_id` / `app.source` per transaction. Until shared sign-in (step 5) the person may be NULL; the log then records the database role and the source. Step 5 takes the person from the signed-in JWT.
7. **Log scope (F).** Logged: the graph tables (`objects` and its 1:1 suffixes, `relationships`, classification, information containers and revisions, model revisions, BCF topics, saved views, IDS documents, clash tests and reviews, drawing link overrides, GUID aliases, captures, the manifests) and, in an AIMforked PR, the platform tables (D-188). Not logged: the `ifc_rev_*` revision copy (derived from the archived file; its sha256 is the audit), run result tables, `mcp_call_log`, `ifc_guid_history`, `bcf_topic_counters`.
8. **ETL loads (G).** The log trigger fires only when the row changed (`old.* is distinct from new.*`), so no-op rewrites log nothing; real changes are logged per row with the source `etl:<run>`, plus one summary row per run.
9. **Storage (H).** Schema `audit`, one table partitioned by month (plus a default partition), before and after as full `jsonb` rows, indexes on time, row and project. Append-only: owned by a NOLOGIN role, written only through a SECURITY DEFINER trigger function, no role holds insert, update, delete or truncate, and a guard trigger rejects update and delete. IfcOwnerHistory (creation, last change, person, application, ChangeAction) is a view and function over the log.
10. **Order (I).** PR 1 R10 columns and report; PR 2 audit schema, public triggers, pre-request, writers; PR 3 R10 warn then enforce; PR 4 AIMforked platform triggers. Each production apply on Samuel's yes, after a fresh database-only backup, a restore test, a rehearsal with the zero-difference check and an ETL load on the restore with the triggers on.

**Rejected:** enforcing at once (would reject writes before the data is clean); letting NULL `ifc_type` pass (weaker than filling the 65 documents); allowing IfcPerson and IfcOrganization at the actor end (contradicts PLATFORM.md §5.3 and the schema); a signed header now (only the server holds the `service_role` key; step 5 replaces the header with the JWT); logging the revision copy (hundreds of thousands of rows per load, derived from a file); one log table per source table.

**Addendum (PR 3, 5 Nov):** the check runs on insert and on an update that changes `rel_type`, `from_id` or `to_id`. An update of other columns is not rechecked: under `enforce` an old edge that fails could otherwise not be closed (`valid_until`), and the ETL's rewrites of unchanged edges would pay the check every load. A rel_type moves to `enforce` with `supabase/pending/relationship_ifc_enforce.sql` (copied into a migration on Samuel's yes); `rel_assigns_to_actor` stays `warn` until the ETL writes IfcActor nodes.

**Consequences:** a new rel_type needs its end attributes (or explicit types for aim_*) in the generator. Every writer sets the person and the source (AGENTS.md). IfcEvent stays the domain record of workflow transitions (R11); the log is the technical audit.
